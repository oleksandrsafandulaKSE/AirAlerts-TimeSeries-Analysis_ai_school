## A. Live forecast archive and check (Netlify functions, `netlify/live/lib/`)
- **A1. Snapshots.** Today `runner.mjs` writes `snap/<UTC hour>` on every minute run (last write in the hour wins)
  and keeps 7 days. Change: **the first successful write in a UTC hour wins**:
  - the run reads `snap/<hour>` first and writes only if it is absent; Netlify Blobs has no create-if-absent, so a
    rare race between two overlapping runs can overwrite; the stored snapshot carries `written_at`, and the scorer
    uses the snapshot's own τ, so a race changes which forecast is archived, never how it is scored;
  - a snapshot with τ ≥ hour start + 15 min (missed runs) is kept but flagged `late` and NOT scored, so every
    scored forecast was issued in [hour, hour + 15 min); τ = hour + 15:00.000 exactly is late;
  - migration: snapshots written before the change (last-write) are tagged `legacy` by key date (< deploy time,
    read from a `check_epoch` blob set on the first new run) and not scored;
  - retention → 35 days (≈ 840 small blobs). Each snapshot already holds τ and per-unit `p`, `state`,
    `recent_rate`, `caution`; only `written_at` is added.
- **A2. Scoring function** `scoreSnapshots(state, snapshots, now, regions)` in a new `lib/check.mjs`.
  **Estimand (PROVISIONAL):** skill on rows that were eligible BOTH as issued AND after reconciliation — the
  conservative intersection, so no scored row is under alert at τ in either view (D-003 holds for scored rows):
  - a snapshot is scored only when `now ≥ τ + 1 h + SETTLE` (SETTLE = 3 h; every unit is history-refreshed every
    24 min by the rotation) AND the unit's confirmed coverage (`coverageAt(state, u, now)`) covers the WHOLE
    label window [τ − 24 h, τ + 1 h] continuously (the 24 h look-back so an unrecorded alert that would make the
    unit under alert at τ is excluded, as the D-022/D-023 post-gap rule does); any hole → not scored;
  - as issued: snapshot `state == "forecast"`, p and recent_rate present, and `caution` contains neither
    `rejected_history_record` nor `rejected_active_record` (rejected records = unknown label contamination);
  - after reconciliation: the unit is not under a non-standing alert (D-020 cap) at τ in the alerts as known at
    `now`; otherwise not scored and counted as "reconciled under alert";
  - rejections discovered later: `state.rejections` expire after 24 h (`REJECT_KEEP`), so the runner also appends
    every rejection (at, unit, where) to a persistent `rejection_log` blob kept 35 days (existing behaviour of
    `state.rejections` unchanged). A row (unit, τ) is not scored if that unit has ANY logged rejection with
    at ≥ τ − 24 h (up to the scoring time), counted as "rejected after issue";
  - y = 1 iff a merged-unit onset (same union and D-020 cap as `featuresAt`, all API alert types per M8) falls in
    (τ, τ + 1 h], from the alerts as known at `now` (labels may use later knowledge; p and recent_rate are read
    only from the stored snapshot, never recomputed);
  - outputs: overall, per group and per UTC day — rows, positives, base rate, Brier of p, Brier of recent_rate,
    BSS = 1 − ΣB_p / ΣB_rr (pooled, never averaged); BSS = null with reason "no rows" or "zero reference loss"
    (D-025 style); reliability in 10 bins [0, 0.1), …, [0.9, 1.0] (p = 1 in the last bin): rows, mean p, observed
    rate; per unit: rows, Brier p, Brier recent_rate. Low-n flag when rows < 200 or positives < 20. Exclusion
    counts by reason (late, legacy, unsettled, coverage hole, not forecast, rejected, reconciled under alert);
  - stored as blob `check`, recomputed at most once per UTC hour by the scheduled function (guard on the stored
    `check.computed_hour`).
- **A3. History endpoint** `GET /api/history` (new `netlify/functions/history.mjs`), one payload for all 24 units:
  - last 7 days of hourly snapshots (τ, p, state, recent_rate, late/legacy flags);
  - last 14 days (for §B2b) of, per unit: **physical alerts** (raw start/end as known now, open ones flagged) and
    the **capped state** intervals (D-020: an alert counts as "under alert" only for its first 24 h; an alert of
    exactly 24 h is capped at exactly start + 24 h; overlapping alerts are merged), onsets, and the confirmed
    coverage intervals, so the page can tell "no data" from "no onsets".
  `GET /api/check` returns the `check` blob. Neither returns the token or raw API records.
- **A4. Tests (node --test, `netlify/live/test/check.test.mjs`):**
  - an onset exactly at τ is NOT counted, one exactly at τ + 1 h IS counted;
  - a unit under alert at τ (snapshot state `alert_running`) is not scored even if an onset follows;
  - an unsettled snapshot (now < τ + 4 h) and an unconfirmed coverage are not scored;
  - BSS is the pooled ratio (a fixture where averaging per-day skill would give a different value);
  - model = recent rate → BSS exactly 0; reliability bins sum to the row count;
  - a coverage hole inside [τ − 24 h, τ + 1 h] → not scored, even when coverage is confirmed until a later time;
  - `state == "forecast"` with a `rejected_history_record` caution → not scored;
  - a clean snapshot whose unit gets a history rejection logged at τ + 2 h (after issue, after `REJECT_KEEP` of
    an earlier one expired) → not scored; a rejection logged at τ − 24 h − 1 ms → does not exclude; the
    `rejection_log` keeps entries 35 days and survives the 24 h expiry of `state.rejections`;
  - late boundary: τ = hour + 14:59.999 is scored, τ = hour + 15:00.000 is late;
  - **B2b pattern function** lives in `netlify/live/lib/pattern.mjs` and is inlined into the page by
    `build_site.py` (same code tested and shipped). Fixtures: the 25-hour day 2025-10-26 (repeated 03:00 Kyiv:
    the 03–06 block holds 4 real hours, onsets in both 03:30 instances land in it), the 23-hour day 2026-03-29
    (skipped 03:00: the 03–06 block holds 2 real hours); a partial first day (history starts 10:00 Kyiv → blocks
    before are "no data"); a block with a 30-min coverage hole → "no data", not 0; a fully covered block with no
    onsets → 0;
  - reconciliation finds an alert that started before τ and was active at τ → not scored ("reconciled under
    alert"), although the snapshot said "forecast";
  - **isolation / negative controls:** after archiving, change later ends, add reconciled records and add new
    onsets: the stored p and recent_rate used by the scorer are byte-identical; a deliberately leaky scorer that
    recomputes recent_rate from final data (including labels with s > τ − 1 h) gives different values and the
    test detects it;
  - BSS null for no rows and for zero reference loss; p = 1.0 lands in the last bin;
  - first-write-in-hour: two runs in one hour leave the first snapshot unchanged; a snapshot written at
    hour + 16 min is `late` and not scored; legacy keys are not scored; retention deletes only keys older than
    35 days;
  - Kyiv City and Kyivska with different alerts stay separate through history, check and group totals;
  - existing `runner/live/lgb` tests and the Python parity test (`tests/test_live_parity.py`) still pass.

## B. Site analytics (`site_src/template.html`, `scripts/build_site.py`)
Same visual system as today; new blocks reuse the existing chart helpers, colour tokens, dark mode and phone
layout.
- **B1. Oblast panel (live map).** Click/tap an oblast: chance of a new alert in the next 60 min; the two-week
  rate (`recent_rate`) next to it, labelled "simple rule"; state (under alert since HH:MM Kyiv; "standing alert:
  counted only for its first 24 h" per D-020; data gap); onsets in the last 24 h; **neighbours under alert now =
  neighbours in the capped state** (the model's definition), with physical-but-standing neighbour alerts listed
  separately; cautions in plain words. Keyboard-accessible (Enter on a focused oblast).
- **B2. Last 7 days strip** (from `/api/history`): hourly forecast line, physical alert bands (light) with the
  capped "under alert" part (strong), onset ticks; hours without a snapshot are a grey gap, never 0%; hours
  without confirmed coverage are marked "no data"; under-alert hours hatched (no forecast by design).
  - **B2b. Recent pattern** (descriptive): 14 Kyiv calendar days × 8 three-hour Kyiv blocks of onset counts for
    the oblast; caption "what happened, not a forecast". Blocks come from `Intl` Kyiv local time of each onset;
    on DST days a block is the local clock interval (one block has 2 or 4 real hours, noted in the tooltip); a
    block not fully covered by confirmed coverage shows "no data", not 0; partial first/last days are shown as
    partial.
- **B3. Live check section** (from `/api/check`): tag "Exploratory · live API data · not part of the study";
  BSS vs the two-week rule per day (bars) and cumulative; reliability (10 bins); rows/base rate; low-n warning;
  per-oblast table. Text states the number of days scored.
- **B4. Replay of the final test (study section).** Map animation over 27 Jul – 7 Sep 2026, hour by hour, from the
  existing `payload["timeline"]` (frozen H = 1 `p_model`, `p_recent_rate`, status per unit-hour): colour = p_model;
  outline = onset in (t, t + 1 h]; hatched = masked (under alert); grey = gap / missing feature / not scored.
  Slider, play/pause, +1 h, speed. Running counter up to the slider time: scored rows, Brier model vs two-week
  rule (pooled). Labelled "frozen predictions, test scored once on 2026-10-13". Cumulative sums of per-row losses
  of already published predictions; the end value equals the full-precision `brier_skill_vs_recent` of
  `reports/official/metrics.csv` (overall, model; −0.010064344018558602) to 1e-12, rounded only for display.
- **B5. Stability charts:** per-week BSS bars and day vs night, by group, from `reports/m10/stability_validation.csv`
  (and `stability_test_posthoc.csv` only if M10 §E ran, labelled post-hoc).
- **B6. M10 results:** label-variant table (A1/A3), recency and exposure fold tables, with the M10 wording.
- **B7. `build_site.py`:** reads the new reports; missing optional M10 files → the section says "not run yet"
  (not a silent fallback: the reason is printed by the build and shown on the page); required files still raise.

## C. Testing (Python, `tests/test_site.py`)
- payload has `timeline` hours = 1,008 test hours × 24 units, status codes as today;
- replay prefixes: the cumulative pooled BSS computed by the page's JS function (run under node on the payload) at
  3 pinned prefix hours equals a pandas recomputation from `reports/official/test_predictions.csv` filtered to
  `status == "scored"` and t < prefix, to 1e-12; the final value equals metrics.csv as in §B4; a shuffled-hours
  or unit-misaligned payload fails the prefix check;
- gap pins (checked against `test_predictions.csv`, status counts scored 13,116 / under_alert 6,397 /
  gap_or_missing 3,480 / feature_missing 1,199): every unit-hour in [2026-08-28 23:00, 2026-09-04 00:00) has
  `gap_or_missing` (the H = 1 hour before the gap included); every unit-hour in [2026-09-04 00:00, 2026-09-07 00:00)
  is `feature_missing` or `under_alert` (D-024); no `scored` row after 2026-08-28 22:00; the replay's per-status
  counts equal these; Kyiv City and Kyivska rows are distinct in the replay;
- M10 blocks: present when the CSVs exist, a "not run yet" marker when they do not; numbers equal the CSVs;
- every API-derived block carries the exploratory label; no API number appears in an official table;
- the built `site/index.html` contains no token-like string (regex for `ALERTS_IN_UA_TOKEN` values / bearer).

## Risks / assumptions
- The live check needs days of uptime before it means anything; the page says so and shows the day count.
- Netlify Blobs list/read of 168 snapshots per `/api/history` call: if too slow, cache the assembled history in a
  blob updated once per hour by the scheduled function (decided during implementation only if measured > 2 s).
- First-write-wins changes which forecast is archived for each hour; the hourly snapshot was never published as a
  metric, so nothing already reported changes.
