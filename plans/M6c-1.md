## 1. Goal
Train and evaluate, on alerts.in.ua history only, per oblast at every hour t, three binary onset forecasts
P(an ANY / YELLOW / RED alert starts in (t, t+H]), for H = 1 (headline) and H = 3. Report model, baselines and the
blend separately, on validation and (once) on one test week, plus a reliability plot and the chart (Brier skill vs
the recent-rate baseline per type + the blend weight over time). Keep the pipeline callable as one function / CLI
with explicit cut-off dates so M6b (monthly job) reuses it unchanged.

Out of scope: the monthly job (M6b), the site (M6-site), README, any edit to `src/*.py`, `scripts/run_all.py`
(hashed by `run_all.code_fingerprint`, pinned by `tests/test_improve_models.py`), `collect/`, `datastore/`,
`reports/collect/`, `.github/`, `extras/`, `netlify/`, site files. No API call, no token. No new dependency.
Testing the frozen official model's prediction as an INPUT feature (allowed by the definition) is left to a later
milestone (one more moving part on 2 weeks of data).

## 4. Targets, masks, splits
- Types: ANY = all air-raid alerts (yellow ∪ red); YELLOW = `alert_level == "yellow"`; RED = `alert_level == "red"`.
  Per type, the alert subset goes through the unchanged `src.grid.unit_intervals` (D-002 union over all location
  levels, D-020 24 h cap, merged intervals): typed onset = start of a merged interval of that type (plus the
  zero-duration rule of `unit_intervals`). The yellow subset is filtered in `newregime/data.py` and passed with
  `target_levels="any"` (src `filter_levels` has no "yellow"; `src` is not edited); red uses the same pre-filtering
  for symmetry (identical to `filter_levels("red")`, asserted in a test).
- y_T(t) = 1 iff a type-T onset lies in (t, t+H]. mask_T(t) = type-T active at t (under the 24 h cap) OR gap/hole/
  history-start mask. So a red onset during an active yellow counts for RED, and vice versa (D-033). A test asserts
  no unmasked row is active for its own type, and that a red onset inside yellow is y_red = 1 on an unmasked row.
- Grid: hourly UTC, t = start of hour, from `grid_start = 2026-09-13 00:00`. The history-start zone [EPOCH,
  history_start) + 24 h post-zone mask comes from `src.config.mask_gaps` with `history_start` set (as in M4).
- Split (`first_split()`, half-open, UTC, D-021): train [2026-09-13 00:00, 2026-10-04 00:00), validation
  [2026-10-04 00:00, 2026-10-11 00:00), test [2026-10-11 00:00, 2026-10-17 19:00). Test end = coverage_end floored to
  the hour (the last full hour whose labels are all known; derived from the pull log, not hard-coded, and asserted
  equal to 2026-10-17 19:00 for this split). Per H, `grid_end = test_end − H + 1 h` so the last label window ends at
  test_end ≤ coverage_end (`src.grid.build_grid` check).
- Purge (CLAUDE.md, D-021): `src.evaluate.eligibility` per split keeps t + H ≤ split end; plus mask == 0, y known,
  no NaN feature (D-024).
- Effective training start: `onsets_last_7d` is NaN while (t − 7 d, t] touches the history-start zone, i.e. until
  2026-09-20 17:00; with D-024 those rows are dropped, so the fit set is ≈ 2026-09-20 18:00 → 10-04 (≈ 2 weeks).
  Printed; this is the recipe, not changed here.
- Test labels are blanked (`src.evaluate.isolate_test_labels`, t + H > test start) in the fit stage before any
  model, baseline table or blend weight is computed.

## 6. Models, baselines, blend
- Model per type × H (6 models): `src.model.train` (PARAMS, MAX_ROUNDS, EARLY_STOPPING unchanged; LightGBM on
  eligible TRAIN rows, early stopping on eligible VALIDATION rows, no refit), frozen at `best_iteration`; then the
  pre-registered validation calibration rule `src.model.calibration_decision` (Platt iff val ECE > 0.02) +
  `apply_calibration`. Headline "model" = calibrated output.
- Frozen official comparison line (ANY only): `reports/official/model.txt` (H = 1) and
  `reports/official_h3/model.txt` (H = 3) via `src.model.Predictor`, after checking the sha256 of model.txt and
  calibrator.json against their `preregistration.json` and reproducing their `val_predictions.csv` exactly. Scored on
  the same ANY rows (same features). Not trained or tuned.
- Baselines per type (refit per type on that type's eligible TRAIN rows; `src.baselines.fit_tables` +
  `predict_from_tables`, typed alerts passed for raw persistence): climatology, recent_rate (MAIN, rolling 14 d over
  rows s ∈ [t − 14 d, t − H] with known labels, shrunk (k + 10·p_unit)/(n + 10), p_unit = the unit's TRAIN rate of
  that type), persistence_raw, persistence_calibrated.
- Extra baseline (RED only, `recent_any_x_red_share`), defined on COMMON SUPPORT: rr_any(t) × share(t).
  rr_any(t) = the ANY rolling recent rate at t, computed by `src.baselines.recent_rate` from the ANY label history; it
  needs only past ANY labels, so it exists on every RED scoring row, including rows where ANY is masked (a yellow is
  active). share(t) = (k_red + 10·π_u) / (k_any + 10), where both counts run over the SAME rows: the unit's
  ANY-eligible rows s ∈ [t − 14 d, t − H] with both labels known (ANY-eligible ⊂ RED-eligible, since ANY inactive ⇒
  RED inactive); k_red = Σ y_red(s), k_any = Σ y_any(s) on those rows. π_u = the same ratio on the unit's ANY-eligible
  TRAIN rows (0 if k_any = 0). Clipped to [0, 1] (on common support a red onset in (s, s+H] with ANY inactive at s
  implies an ANY onset in (s, s+H], so share ≤ 1 except for zero-duration edge cases). Known approximation, stated in
  the report: on RED rows where yellow is active, rr_any is the rate for an "any-inactive" state.
- Blend per type × H: p_blend(t) = w(t)·p_model(t) + (1 − w(t))·p_recent(t), w(t) = n/(n + 50)·clip(w*, 0, 1),
  w* = Σ(p_b − y)(p_b − p_m) / Σ(p_m − p_b)² (w* = 0 if the denominator is 0), one weight pooled over all 24 units.
  WINDOW ROWS W(t) = the eligible rows s (all units) with s ∈ [t − 28 d, t − H] AND s ≥ the model's fit cut-off
  (train end = 2026-10-04), so w* never uses in-sample (training-row) predictions; p_b, p_m are the recent-rate and
  calibrated model predictions on those rows. n = number of DISTINCT type-T ONSET EVENTS (unit, onset time o, merged
  onsets from `unit_intervals`) such that o ∈ (s, s + H] for at least one row s ∈ W(t) with y(s) = 1 (so for H = 3
  one onset that makes three rows positive counts once; the definition says "onsets"). Before a model's fit cut-off,
  w = 0. w is computed for every hour of val + test and saved.
- Two readings of the blend, labelled so they are never confused:
  (a) TEST WEEK (causal, the reported blend): the 6 models and their calibrators are frozen before any test label is
  read (fit stage, test labels blanked); at a test hour t the window rows are validation rows plus test rows with
  s ≤ t − H, all labels known at t. So w(t) and p_blend(t) on the test week use only information known at t.
  (b) VALIDATION WEEK (RETROSPECTIVE DIAGNOSTIC, not causal): the model was early-stopped and calibrated on the whole
  validation week, so its validation predictions depend on later validation labels. Validation w(t) and blend
  metrics are reported in a separate block titled "retrospective diagnostic", never as a causal forecast result.
- Calibration of the blend: none (it is a convex mix of two predictors).

## 8. Tests
`tests/test_newregime.py` (synthetic alerts unless stated; fast):
1. Typed targets: a red alert starting inside an active yellow → y_red = 1 on an unmasked row, row masked for YELLOW;
   the symmetric case; y_any = 0 there (any already active). No unmasked row has its own type active.
2. Pre-filtered red == `src.grid.filter_levels(…, "red")` intervals.
3. `other_level_active_at_t` equals the other type's grid `active_at_t`; NaN inside zones.
4. Coverage from a toy pull log: history_start / coverage_end values; a unit without a pull raises; a recorded hole
   → masked rows [hole_from − H, hole_to + 24 h) and NaN 7-d features across it.
5. Split: test_end = floor_hour(coverage_end); every eligible row has t + H ≤ its split end (H = 1 and 3).
6. Blend: w* matches a hand computation; denominator 0 → 0; clip; n0 shrinkage; rows before the fit cut-off ignored;
   w = 0 before the cut-off.
7. Red-share baseline matches a hand computation; clipped to [0, 1].
8. Test-once guard: `score_test` twice raises; `fit` after the marker raises; a tampered model file fails the
   pre-registration check.
9. Real datastore smoke (committed file): 24 units, coverage values as in §3, ANY/YELLOW/RED onset counts printed and
   > 0, no unmasked row active for its own type.

10. Pinned typed witnesses (synthetic, per type ANY/YELLOW/RED, H = 1 and 3): an alert with unknown `finished_at`
    (open) is active exactly until start + 24 h and stops masking at start + 24 h (D-020); an alert ending exactly at

    t + H = split end is KEPT, a row with t + H = split end + 1 h is purged (D-021/D-022 boundary); calendar features
    across the Kyiv DST end 2026-10-25 (01:00 UTC; t = 00:00 and 01:00 UTC both give hour_kyiv = 3, asserted
    exactly, and the label window stays (t, t+H] in UTC); a synthetic

    both hole edges. (The official 29 Aug–2 Sep gap is not in API data; its edges stay tested by the official
    suite.)

`tests/test_newregime_leakage.py` (ts-leakage-audit skill):
11. Truncation invariance on the REAL datastore: for 5 forecast times (one in each split, one right after the 7-d
    NaN window ends, one at a Kyiv day boundary), for EACH type, features (incl. `other_level_active_at_t`) built
    from the reconstruction at coverage_end equal those built from `as_reconstructed_at(rows, t)`, for all 24 units.

## 9. Risks / assumptions
- Tiny data: ≈ 2 weeks of eligible training rows after the 7-d look-back (§4), 1 validation week, 1 test week.
  Early stopping on 1 week may stop very early; RED has ≈ 1,100 onsets total, concentrated in 3 oblasts. Results
  are exploratory; negative skill vs recent rate is a valid result and will be reported as such.
- Validation week does triple duty (early stopping, Platt, the start of the blend window) — mild optimism, stated.
- Event-time reconstruction uses later corrections (`updated_at`) — not a live replay.
- Holes mapped to national gaps is conservative (masks units that were covered); acceptable while holes are rare.
- No DST change inside the data (the next one is 2026-10-25).
- Runtime: build is per type × H on ≈ 840 h × 24 units; a few minutes total.
