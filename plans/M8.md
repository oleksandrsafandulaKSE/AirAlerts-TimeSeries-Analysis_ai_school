# M8 plan v1 — Live map of Ukraine: next-hour forecasts, auto-updated by a Netlify scheduled function

Status: AGREED (consensus round 5, D-026). See reviews/M8-consensus.md. Human decisions in chat (2026-10-13): "the UI has to be an
interactive map of Ukraine that auto-updates, not a Claude artifact"; live next-hour forecast; the OFFSET model (adapts
to the recent level); a Netlify scheduled function; geoBoundaries ADM1 boundaries. This starts part of M6 (D-016) by
the human's explicit decision. Further human decisions after round 1 (chat, 2026-10-13):
(a) **forecast period = the next 60 minutes from the moment of the update**, (τ, τ + 1 h] with inputs ≤ τ — a deliberate
change of forecast-time definition vs training (forecasts at hour starts), labelled on the page and in proposed D-032;
(b) **all API alert types** count (air_raid + artillery_shelling + urban_fights), for labels, features and masks — this
also resolves the open M4 question for the exploratory section; (c) dependencies approved: `@netlify/functions@2.8.2`,
`@netlify/blobs@8.1.0` (exact pins); (d) D-014 wording ratified: a training row is kept iff t + H ≤ cut-off. Rules: CLAUDE.md (token never printed/logged/committed; ≤ 2 API history requests/min;
never mix sources in one training set or metric), D-007, D-015, D-020, D-023, D-025, D-027, D-030 (proposed).

## 1. Goal
A public page on Netlify: a real map of Ukraine's oblasts coloured by the chance that a NEW alert starts in the next hour,
recomputed automatically (every minute) from live alerts.in.ua data, plus the current alert state. The study results
(frozen headline, M7 post-hoc rows, timeline) stay on the same site as a separate "How well does it work?" section.
This is an operational forecast, NOT a new evaluation: no metric is reported on live data in M8.

## 2. Architecture (no Python on Netlify)
- **Model export (offline, Python):** the M7 V2 recipe exactly: official data only; fit = eligible rows in
  [2022-03-23, 2026-06-29) with t + H ≤ 2026-06-29; early stopping on eligible rows in [2026-06-29, 2026-07-27) with
  t + H ≤ 2026-07-27; `model.PARAMS` unchanged; features = `features.FEATURES` in that order, `unit_code` = index in
  `regions.units()` (categorical); offset r = (k + 10·q)/(n + 10) over eligible hour rows s ∈ [τ − 14 d, τ − 1 h], prior q =
  the unit's expanding eligible-label rate over all history available at τ (national pooled fallback; none → no forecast),
  clipped to [1e-4, 1 − 1e-4] before the logit. Saved: `model_live.json` (`dump_model`, trees up to `best_iteration`) +
  `model_live_meta.json` (features, category order, offset constants, best_iteration, dates, sha256). No tuning; no API
  data in training.
- **Inference in JavaScript:** `netlify/live/lib/` evaluates the LightGBM trees from the JSON dump (numerical splits
  and the categorical `unit_code` split), computes the 9 base features + the causal offset from an alert history, and
  returns p = sigmoid(logit(r) + margin). Parity is tested against Python on the saved API dump (§5).
- **State (Netlify Blobs):** `alerts` = versioned alert records (shared format + `alert_id`, `updated_at`, `alert_type`,
  `first_seen_at`, `end_seen_at`, `end_source` ∈ {active-disappearance, history}, `history_reconciled_at`); `coverage` =
  per unit a LIST of (possibly disjoint) confirmed intervals [from, to): a successful history call at time c always
  confirms [c − 30 d, c) for that unit and is merged with overlapping/touching intervals; any stretch not covered by any
  interval is a HOLE (e.g. after an outage longer than the endpoint's 30-day window, the unrecoverable stretch stays a hole
  while fresh coverage after it is recorded normally); `status` =
  last run outcome (ok / api_error / rate_limited + time), stored SEPARATELY from the forecast. Seeded once from the saved
  dump via a one-off upload script (coverage = its fetch times). Unit mapping: each API alert's `location_oblast` → unit by
  exact match of `regions.py` `api_oblast_name` (Kyiv City "м. Київ" vs Kyivska "Київська область" separate; unknown names
  raise AFTER the deliberate exclusions — Luhanska, Crimea and Sevastopol are recognised by their API names listed in
  `regions.py` (`EXCLUDED_API_NAMES`, alongside `EXCLUDED_API_UIDS`), skipped and counted); all administrative levels are
  unioned per unit (D-002), the D-020 cap and D-023 merging are unchanged.
- **Scheduled function `update-forecast` (every minute, ≤ 30 s):** (1) one request to the ACTIVE-alerts endpoint (token
  from the Netlify env var `ALERTS_IN_UA_TOKEN`, never logged); new ids → new records (`first_seen_at` = poll time);
  (2) ONE `month_ago` request per run for the next unit in a fixed rotation (24 units → each unit reconciled every ~24 min;
  1 history request/min < the 2/min limit); it supplies exact start/end times and alerts that started and ended between
  polls; ids that vanished from ACTIVE but are not yet reconciled keep an UNKNOWN end (D-027: treated as open, 24 h cap),
  never a guessed end; (3) τ = the run time (UTC, to the second); compute inputs from records as known at τ (versions with
  first_seen_at / reconciliation time ≤ τ only) and forecast (τ, τ + 1 h]; (4) write `forecast/latest.json` (τ, per unit
  p or reason, physical alert status, capped mask status, coverage age) + a timestamped copy (7 days kept); `status`
  updated on every run, success or failure.
- **Missing data, live (D-022–D-024 analogues).** LABELS (offset k, n, prior q) use ONLY history-confirmed hours: a label
  hour s counts iff its whole label window [s, s + H] lies inside one confirmed interval AND s is outside every hole's
  extended zone [h0 − H, h1 + 24 h) — exactly the hours `grid.gap_mask_for` masks around the official gap (label touches
  the hole, or post-hole state unknown). Poll-only hours never supply labels.
  EVENT inputs (alert state at τ, recent onsets, time since, neighbour/national state) may use, for the unconfirmed tail
  after the latest confirmed time (≤ ~25 min), the ACTIVE-poll record — **human-approved live-mode exception (chat,
  2026-10-13; proposed D-032)**: alerts shorter than the poll spacing (~1–2 min) can be missed there until reconciliation;
  stated on the page. Everything else uncovered is a hole [h0, h1); its EXTENDED zone [h0, h1 + 24 h) is handled exactly like
  `config.uncertainty_zones` handles the official gap (a visible start right after a hole may continue an unseen alert, so
  it is not a certain onset):
  - the unit's own windowed inputs (onsets 24 h / 7 d) → unknown if the window intersects the unit's EXTENDED zone;
    time-since inputs → unknown if τ ≥ h0 and the last event is before h1 + 24 h (the D-023 rule in `features.py`);
  - post-hole uncertainty (D-022/D-023 analogue): for 24 h after a hole ends, the unit's alert STATE is unknown (an
    unrecorded alert from inside the hole could still be within its 24 h cap) unless backfill has confirmed the hole;
  - national and neighbour inputs → unknown if the relevant window intersects a hole, or τ lies in the post-hole 24 h
    zone, of ANY unit involved (all 24 for national, the neighbours for neighbour inputs);
  - any unknown model input → no probability for that unit; the map shows "data gap" with the hole's dates. Holes stop
    blocking once backfill (a later history call reaching the hole) confirms it, or once they leave every look-back window.
  A failed ACTIVE poll for > 5 min is itself a national hole.
- **Read function `forecast` (HTTP GET):** returns ONE JSON object `{status, forecast}` (the separately stored `status` of
  the last run + `latest.json`) with `Cache-Control: max-age=30`. The page fetches it on load and every 60 s; no token or
  raw API data reaches the browser.
- **Stale-data rule:** on every fetch the page checks `status` and the forecast time: if the last run failed, or the forecast
  is older than 5 minutes, it shows "data delayed since HH:MM" and greys the map at that fetch (≤ 60 s after the failure is
  recorded) — never a silently old forecast. Tested end to end: a failing run → the GET payload carries the failure → the
  page greys.

## 3. Page
- **Map:** geoBoundaries UKR ADM1 (derived from OpenStreetMap, licence ODbL 1.0 — corrected from "CC BY 4.0" after checking the release metadata; attribution under each map), simplified (≤ 150 KB), projected offline to SVG
  paths in Python (`scripts/build_map.py`); Kyiv City drawn as its own small shape inside Kyivska; Crimea and Luhansk
  drawn grey "not forecast". Colour = chance of a new alert in the next 60 minutes (sequential, validated palette). Two
  separate statuses: "alert running now" (physical, any active alert of any age, shown as an outline/icon) and "no forecast
  now" (the capped D-020 mask: a non-standing alert ≤ 24 h old is running — hatched). A unit under only a > 24 h standing
  alert IS forecast (D-020), with the outline shown; hover/tap → oblast card: chance, recent rate, alerts in the last
  24 h, last alert start, time of the forecast.
- **Header:** "Chance of a new alert in the next 60 minutes" with the subline "any alert type: air raid, artillery shelling
  or street fighting (alerts.in.ua)", the forecast hour (Kyiv time), last update, a plain
  caveat: "experimental; trained on data before the September 2026 alert reform; not validated on post-reform data;
  not an official warning — always follow official alerts".
- **Below:** the study section (from M5b: short answer, tile map → replaced by the real map in "study" mode, timeline,
  technical details), unchanged numbers.

## 4. Safety and honesty rules
- Never a call to action; the page links to official alert sources and says it is not a warning system.
- The model label in the UI: "offset model (M7 V2 recipe), post-hoc, not validated on post-reform data".
- Token: Netlify env var only; tests grep the repo and the built site for the token value / the env-var read outside
  the function; function logs never include headers or the token.

## 5. Tests
- JS tree evaluator == Python LightGBM `predict(raw_score=True)` on 10,000 rows (max abs diff < 1e-9), incl. the
  categorical split and missing values.
- JS features + offset == Python (`features.build_features` + an offset reference implemented in Python from the same
  definition) on the API dump at 20 times AND on the official data at the two 2025 DST switches, the recording-gap edges
  (D-022–D-024 NaN rules via a config with the approved gap), an alert open in the dump, a > 24 h alert, Kyiv City vs
  Kyivska, and boundary cases: an onset exactly at τ (not in the label window), at τ + 1 h, at a look-back edge, an alert
  exactly 24 h old.
- Raw-data truncation: inputs at τ from the store truncated at τ (records first seen after τ dropped; ends known after τ
  hidden; reconciliations after τ ignored) equal the inputs computed live; replay of a recorded poll sequence reproduces
  the same forecasts. Negative controls caught at pinned witnesses: an input using a reconciled end not yet known at τ;
  an offset window that includes immature label hours τ − H < s ≤ τ (its witness: a unit with an onset in (s, s + H] for
  such an s, so the leaky value differs from the truncated one); the real offset must equal its truncated value there.
- History update: new / disappeared / reappearing ids, duplicate ids keep the latest PARSED `updated_at`, a vanished id
  stays open until reconciled, rate-limit rotation (never > 1 history call per run), clock skew; raising checks for
  schema, unknown oblast names, alert_type values, unit coverage; counts and ranges logged (no token, no headers).
- Causality: the forecast at hour t from history truncated at t equals the one computed later (same JS path).
- Stale-data rule incl. immediate greying on a failed run (status separate from forecast); token never in output; map file
  valid (24 units + 2 grey, ids match `regions.py` keys).
- Function handler unit tests with a mocked fetch and an in-memory Blobs stub (no network).

## 9. Limitation (human-approved exception)
An alert that starts and ends between two successful polls (< ~2 min) is seen only after its unit's next history
reconciliation (≤ ~24 min). Until then it can be missing from EVENT inputs (never from labels, which use confirmed hours
only). Approved by the human as a live-mode exception; stated on the page; proposed D-032.
