# Roadmap M1–M5 (+ M6 future work), general level

What each milestone delivers and when it counts as done, not how. Step-by-step plans are
written per milestone in the implementation chat (`plans/M<n>.md`), each reviewed by Codex
before implementation (D-019). Raw material: `plans/ALL.md`, `reviews/*-codex.md`.

## The question
For each of 24 units (23 oblasts + Kyiv City), at the start of each UTC hour t: what is the
probability that a NEW air-raid alert starts in (t, t+1h], given only what is known at t?
"Under alert" = at least one active non-standing alert (≤ 24h since start, D-020); those hours are masked.
Headline: the frozen model on the last 6 weeks of official data, 27 Jul–7 Sep 2026, primary
metric = Brier skill vs the rolling recent-rate baseline (D-021). Plus an exploratory check on the
new yellow/red system (D-015).

## Milestones

### M1 — Clean data → hourly grid with target and mask
- **Delivers:** official data in the shared format; duplicates removed; Luhanska excluded; per-unit
  merged intervals across all admin levels with the causal standing-alert rule (D-020); the
  recording gap marked as missing (approved boundaries); a UTC hourly grid with `y` and the mask;
  `regions.py`; named run configs; `run_all.py --config` + `run_meta.json`; pinned versions.
- **Done when (pass/fail):**
  - every test passes;
  - mask and target match hand-computed expected states;
  - exactly the 24 canonical units are present;
  - 0 duplicates remain;
  - the only detected gap equals the approved 29 Aug–2 Sep boundaries;
  - no quarter after 2025 has a base rate below 50% of the 2024 average.

### M2 — Features known at t + leakage guarantee
- **Delivers:** own history, neighbour and national state, Kyiv-time calendar features; the
  truncation leakage test on raw data, with a negative control.
- **Done when:** the leakage test passes on real data AND fails on the deliberately leaky feature;
  the DST cases pass.

### M3 — Baselines + evaluation framework (validation only)
- **Delivers:** splits (train all history, validation [2026-06-29, 2026-07-27), test) with the purge
  and the label-maturity rule; four baselines (climatology, rolling recent rate, raw and calibrated
  persistence); the metric suite including the overall reliability plot; `reports/<run>/` output.
- **Done when:** the baseline table **on validation** is reproduced by one command. The final test is NOT scored here.

### M4 — Model + final test + new-regime analysis
- **Delivers:** one pooled LightGBM model, early-stopped on validation, no refit, a calibration check on
  validation; then ONE scoring of the final test for the model and all baselines together, per group;
  the API loader and the exploratory new-regime section (before/after table, the frozen model on
  "any alert", within-unit AUC, calibration-in-the-large; the conclusion conditional on the results).
- **Optional:** red-only row; weekly refit row (D-014); bootstrap CI; reliability plot per group.
- **Done when:** `reports/official/` contains the headline table (Brier skill vs recent-rate,
  secondary metrics, per group) and the reliability plot; `reports/new_regime/` contains its tables.

### M5 — README, figures, Streamlit
- **Delivers:** the complete README, figures generated by `run_all.py`, and a Streamlit page reading
  only saved results.
- **Done when:** every number and figure in the README comes from a `reports/<run>/` file
  produced by `scripts/run_all.py`.

### M6 — Automated data workflow: FUTURE WORK (D-016)
Daily API collection and monthly re-evaluation via GitHub Actions. Not in scope unless the
human starts it. A yellow-regime model needs the human's explicit approval. The next API
fetch must happen before ~10 Nov 2026, or history from after 12 Sep is lost.

## Order
M1 → M2 → M3 → M4 → M5. The human decides scope at the deadline and records what was or wasn't
implemented.
